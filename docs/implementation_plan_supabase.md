# План реализации: рассылка тренировок друзьям через Supabase

## Обзор

Альтернатива P2P (WebRTC): рассылка запланированных тренировок друзьям реализуется через **сервер на базе Supabase**. События создаются локально; в Supabase синхронизируются **только совместные** (приглашения друзьям). Друзья получают приглашения и обновления в реальном времени или при следующем запуске приложения.

**Преимущества подхода:**
- Не нужны WebRTC, STUN/TURN, signaling
- Работает при разном времени онлайна отправителя и получателя
- Единый источник правды на сервере для общих событий
- Realtime в Supabase для мгновенных обновлений

## Модель авторизации и данных

### Автоматическая регистрация и Supabase Auth

При **первом запуске** приложение само регистрирует пользователя в Supabase и сохраняет учётные данные в приложении. Дальше используется обычная авторизация Supabase и RLS.

1. **Первый запуск приложения**
   - Генерируется UUID пользователя (как сейчас) и сохраняется в профиле/QR.
   - Приложение вызывает Supabase Auth **signUp**:
     - **Email:** уникальный, выданный системой, например `user-<app_uuid>@internal.fitapp.local` (или другой домен, без верификации).
     - **Пароль:** случайно сгенерированный (32+ символа), пользователь его не вводит и не видит.
   - Логин (email) и пароль сохраняются **только в приложении** (`flutter_secure_storage` или зашифрованный Hive).
   - В таблицу **profiles** добавляется связка: `id = auth.uid()`, `app_uuid = <наш UUID>`, display_name. Так в БД хранится соответствие «сессия Supabase» ↔ «UUID из QR и друзей».

2. **Последующие запуски**
   - Приложение читает сохранённые логин и пароль и вызывает **signIn** в Supabase.
   - После входа есть сессия и `auth.uid()` — запросы к БД и Realtime идут от имени пользователя, RLS фильтрует данные.

3. **В приложении и в БД**
   - В бизнес-логике и в QR используется **UUID приложения** (sender_id, recipients в событиях — это app UUID).
   - RLS строится через таблицу **profiles**: текущий пользователь = `(SELECT app_uuid FROM profiles WHERE id = auth.uid())`. Политики на `events`: доступ только если `sender_id` или `recipients` совпадают с этим app_uuid.

### Что хранится в Supabase

- **Только совместные события** — приглашения на тренировки с хотя бы одним получателем. В таблице событий: id, тип, название, дата/время, место, описание, длительность, отправитель (app UUID), получатели, ответы, статус, напоминание, даты.
- **Таблица profiles** — связка auth.uid() ↔ app_uuid, display_name.

### Что не попадает в Supabase

- **Индивидуальные тренировки** (без получателей) — только в локальном хранилище (Hive).

### Итог

| Данные                     | Где хранятся        | Синхронизация в Supabase |
|----------------------------|--------------------|---------------------------|
| UUID пользователя          | Локально (профиль) | Через profiles (app_uuid) |
| Логин/пароль (системные)   | Локально (secure)  | —                         |
| Список друзей              | Локально (Hive)    | По желанию (см. фазу 2)   |
| Личные тренировки          | Только локально    | Нет                       |
| Приглашения (с получателями)| Локально + Supabase| Да                        |

## Фаза 1: Настройка Supabase и схема данных

### 1.1 Проект Supabase
- [x] Создание проекта в [Supabase](https://supabase.com)
- [x] Сохранение `SUPABASE_URL` и `SUPABASE_ANON_KEY` (для Flutter — через `flutter_dotenv` или `--dart-define`)
  - Реализовано: `.env` с ключами, пакет `flutter_dotenv`, загрузка в `main()`, доступ через `SupabaseConfig.supabaseUrl` / `SupabaseConfig.supabaseAnonKey`

### 1.2 Аутентификация
- [x] Включить в Supabase Auth метод **Email + Password**; отключить подтверждение email для внутренних адресов (например `*@internal.fitapp.local`).
- [x] При первом запуске: signUp с email `user-<app_uuid>@internal.fitapp.local` и сгенерированным паролем; сохранить логин и пароль в приложении (`flutter_secure_storage` или зашифрованное хранилище).
- [x] При следующих запусках: signIn сохранёнными логином и паролем. Все запросы к БД идут с сессией, доступ — через RLS по `auth.uid()` и таблице `profiles` (app_uuid).
  - Реализовано: `SupabaseAuthService.ensureSession(appUuid, displayName)` в SplashScreen при наличии профиля и PIN; `SupabaseCredentialsStorage` (flutter_secure_storage); инициализация Supabase в `main()` при наличии конфига.

### 1.3 Схема БД (PostgreSQL)

В Supabase хранятся **только данные для синхронизации совместных событий**. Все id пользователей — строки UUID из приложения (тип `text` или `uuid`). SQL-скрипты: **`supabase/migrations/20250210000000_initial_schema.sql`** (см. [supabase/README.md](../supabase/README.md)).

- [x] Таблица **events** (единственная обязательная для рассылки)
  - `id` (uuid/text, PK) — совпадает с локальным id события
  - `type` (text) — workout_invitation | event_update | event_cancellation
  - `workout_name` (text) — legs, shoulders, chest, back, arms, cardio, other
  - `date` (timestamptz)
  - `location` (text, nullable)
  - `description` (text, nullable)
  - `duration` (int) — минуты
  - `sender_id` (text) — **UUID приложения отправителя**
  - `sender_name` (text)
  - `recipients` (text[] или jsonb) — массив UUID получателей
  - `recipient_responses` (jsonb) — объект { "recipient_id": "accepted" | "declined" | "pending" }
  - `status` (text) — pending, accepted, declined, completed
  - `reminder_time` (int) — минуты до события
  - `created_at`, `updated_at` (timestamptz)
  - Индексы: по `sender_id`, по `recipients` (GIN при jsonb/array), по `date`

- [x] Таблица **profiles** (обязательна): `id` (uuid, PK, = `auth.uid()`), `app_uuid` (text, unique), `display_name`, `created_at`, `updated_at`. Нужна для RLS (связка сессии и UUID приложения). После signUp триггер `on_auth_user_created` создаёт запись из `raw_user_meta_data` (app_uuid, display_name).
- [ ] Таблица **friends** — опционально (см. фазу 2). Список друзей может оставаться только локальным.

### 1.4 Доступ к данным (RLS)
- [x] **RLS на таблице `events`** (реализовано в миграции):
  - SELECT: только если `(SELECT app_uuid FROM profiles WHERE id = auth.uid())` равен `sender_id` ИЛИ входит в массив `recipients`.
  - INSERT: только если `sender_id` = `(SELECT app_uuid FROM profiles WHERE id = auth.uid())`.
  - UPDATE: отправитель может менять любые поля; получатель — только свой ключ в `recipient_responses`.
  - DELETE: только отправитель.
- [x] Приложение работает с Supabase **напрямую** (клиент с сессией после signIn); Edge Functions для проверки прав не нужны.

### 1.5 Realtime
- [x] Подписка на таблицу `events` через клиент с сессией. Realtime автоматически учитывает RLS — приходят только строки, доступные текущему пользователю (отправитель или получатель). Дополнительная фильтрация на клиенте не нужна.
  - Реализовано: `EventsRealtimeService` (подписка на postgres_changes, при изменении — загрузка из Supabase и слияние с локальным хранилищем), `eventsListProvider` + `eventsRealtimeSubscriptionProvider`; главный экран обновляется при изменениях. В Supabase для таблицы `events` должна быть включена публикация Realtime (см. [Realtime](https://supabase.com/docs/guides/realtime)).

### 1.6 Миграции
- [x] Создание миграции для таблиц `profiles` и `events`: **`supabase/migrations/20250210000000_initial_schema.sql`**
- [x] Триггер для `updated_at` при UPDATE; триггер `on_auth_user_created` для автосоздания записи в `profiles` при signUp

## Фаза 2: Друзья и профили (опционально)

Список друзей и профиль по умолчанию хранятся **только локально**. В Supabase для рассылки достаточно таблицы `events` и UUID приложения.

### 2.1 Базовый вариант (без друзей в Supabase)
- [x] Список друзей остаётся в Hive; при создании приглашения пользователь выбирает друзей из локального списка.
- [x] В Supabase уходят только события с заполненным `recipients` (UUID выбранных друзей). Проверка «только друзьям» — на клиенте (в UI доступны только локальные друзья).

### 2.2 Опционально: друзья в Supabase
- [ ] Если нужна синхронизация друзей между устройствами или проверка на сервере «отправлять только друзьям»:
  - Таблица **friends**: `user_id` (text, app UUID), `friend_id` (text, app UUID), `created_at`; уникальная пара (user_id, friend_id).
  - При добавлении друга по QR — вставка в `friends` на сервере (через клиент с сессией; RLS разрешает только свои записи).
  - Проверку «recipients — только друзья» можно делать в приложении или через RLS/триггер при вставке в `events`.

## Фаза 3: События (рассылка тренировок)

### 3.1 Какие события уходят в Supabase
- [x] **Только события с получателями** (приглашения друзьям): при создании тренировки с выбранными друзьями — сохранять локально и отправлять в Supabase через клиент с сессией (INSERT в `events`). RLS разрешит вставку только если `sender_id` совпадает с app_uuid текущего пользователя.
- [x] **Индивидуальные тренировки** (без получателей) — только локально, в Supabase не отправлять.

### 3.2 Создание события на сервере
- [x] При создании приглашения в приложении:
  - Сохранять событие локально (как сейчас)
  - Вызвать `Supabase.client.from('events').insert(row)` — клиент уже с сессией после signIn, RLS проверит права автоматически.
- [x] Поля в БД соответствуют модели Event: id, type, workout_name, date, location, description, duration, sender_id, sender_name, recipients, recipient_responses, status, reminder_time, created_at, updated_at.

### 3.3 Получение событий получателями
- [x] При открытии приложения: запрос к `events` через клиент с сессией (например `from('events').select()`). RLS вернёт только строки, где пользователь — sender_id или входит в recipients.
- [x] Слияние с локальным кэшем (приоритет у сервера по `updated_at`). Личные события (без получателей) остаются только в локальном кэше.
- [x] Realtime: подписка на таблицу `events`; RLS автоматически фильтрует — приходят только «мои» события.

### 3.4 Обновление статусов (подтверждение/отмена)
- [x] Получатель нажимает «Подтвердить»/«Отменить» → `from('events').update(...).eq('id', eventId)`. RLS разрешит обновление только своего ключа в `recipient_responses` для получателя.
- [x] При необходимости обновлять общий `status` события (например, при первом accepted).
- [x] Realtime донесёт обновление до отправителя.

### 3.5 Отмена и изменение события
- [x] Отмена создателем: `from('events').update({ type: 'event_cancellation' })` или delete; RLS разрешит только отправителю.
- [x] Редактирование: update полей; получатели видят изменения через Realtime или при следующей загрузке.

## Фаза 6: Безопасность и валидация

### 6.1 RLS и права доступа
- [x] RLS на `events` (см. п. 1.4) обеспечивает: вставку только от своего имени (sender_id = app_uuid); чтение только своих событий (отправитель или получатель); обновление/удаление по роли (отправитель — всё, получатель — только свой ответ).
  - Реализовано в `20250210000000_initial_schema.sql`: INSERT WITH CHECK (sender_id = current_app_uuid()); SELECT по sender/recipient; UPDATE для sender и recipient (ограничение «получатель только recipient_responses» — в приложении, см. view_workout_screen); DELETE только для sender.
- [x] RLS на `profiles`: чтение/обновление только своей строки (id = auth.uid()).
  - Реализовано: политики "Users can read own profile", "Users can update own profile", "Users can insert own profile" с id = auth.uid().

### 6.2 Валидация и конфиденциальность
- [x] Проверка формата дат, типов, обязательных полей на клиенте перед вставкой/обновлением; при необходимости — ограничения (CHECK) или триггеры в БД.
  - Клиент: `Event.validateEventData(event.toJson())` вызывается в `EventsRepositoryImpl.addEvent` и `updateEvent` перед отправкой в Supabase; при разборе ответа — в `Event.fromJson`/`fromSupabaseRow`. В БД: CHECK на type, workout_name, status в таблице events.
- [x] Чужие события не возвращаются — RLS фильтрует по auth.uid() и таблице profiles. Прямой доступ к таблицам только с сессией (authenticated).
  - Политики используют `public.current_app_uuid()` (profiles + auth.uid()); без сессии auth.uid() = null — строки не возвращаются.
